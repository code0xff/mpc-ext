mpc-ext/2-of-3

키를 세 조각으로 나눠 보관하는 크롬 확장입니다. 두 조각은 확장이, 한 조각은 서버가 들고 있습니다. 평소에는 확장만으로 서명하고, 조각 하나를 잃으면 서버 조각으로 되살립니다.

감사 전 · 실자산 사용 금지 DKLs23 · secp256k1 Rust + wasm · MV3 Apache-2.0

매커니즘

셰어 세 개, 서명에 필요한 건 두 개

완전한 개인키는 어디에도 존재하지 않습니다. 세 개의 셰어 중 두 개가 모여야 서명이 만들어지고, 서명하는 순간에도 키가 조립되지는 않습니다. 아래에서 상황을 골라 어떤 셰어가 참여하는지 확인하세요.

크롬 확장 기기 · 암호화 저장소
A
셰어 A서명 참여
B
셰어 B서명 참여
서버 자체 호스팅 가능
C
셰어 C대기 — 평시 미사용
2 / 3 서명 가능 · 서버 통신 없음

평시 서명은 확장 안에서 끝납니다. 서버가 꺼져 있어도 서명할 수 있고, 서버는 사용자가 무엇에 서명했는지 알지 못합니다.

정직한 고지

이 설계가 주지 않는 것

셰어 A와 B는 같은 확장, 같은 저장소, 같은 비밀번호 아래 있습니다. 따라서 잠금이 풀린 확장을 장악한 공격자는 두 셰어를 모두 얻습니다. 그 시점의 도난 내성은 평범한 암호화 지갑과 다르지 않습니다.

이 설계에서 MPC가 실제로 주는 것은 두 가지입니다.

  • 셰어 하나를 잃었을 때의 복구 경로 — 주소를 바꾸지 않고 되살립니다.
  • 디스크에 완전한 키가 존재하지 않는다는 점 — 메모리 스크래핑의 난이도만 올라갑니다.

"서버가 털려도 안전하다"는 참이지만, 뒤집으면 "확장이 털리면 서버가 있어도 소용없다"입니다. 평시 서명에서 서버를 뺐기 때문입니다. 셰어 B를 다른 신뢰 영역(패스키 · OS 키체인 · 별도 기기)으로 옮기는 것이 근본 해결책이고, 후속 과제로 등록되어 있습니다.

실측

브라우저에서 쓸 만한가

라이브러리를 고르기 전에 정한 기준을 실제 구현으로 확인했습니다. 5회 평균이며, wasm 수치는 V8에서 세 파티를 한 스레드로 모두 돌린 값입니다.

동작 네이티브 wasm (V8) 기준 결과
서명 (2파티) 4.4 ms 16 ms 1 s 통과
DKG (3파티) 833 ms 4,920 ms 10 s 통과
키 리프레시 (3파티) 834 ms 4,868 ms 30 s 통과

평시 서명 16 ms. 매일 쓰는 경로에서는 지연이 느껴지지 않습니다. 키 생성과 리프레시는 5초 가까이 걸리지만 둘 다 드물게 일어나는 작업입니다. wasm 번들은 최적화 후 459 KB (gzip 174 KB) 입니다.

결정 기록

되돌리기 어려운 선택들

스택 교체, 프로토콜 변경, 저장 포맷 변경은 ADR로 남깁니다. 폐기된 결정도 지우지 않고 사유와 함께 보존합니다.

ADR-0001
MPC 라이브러리 — silence-laboratories/dkls23
폐기. Apache-2.0으로 잘못 파악했으나 실제로는 비상업 · 철회가능 · 재배포불가 라이선스였고, 오픈소스 프로젝트가 쓸 수 없습니다.
ADR-0002
스택 — Rust 코어를 확장과 서버가 공유
프로토콜을 두 언어로 중복 구현하면 두 구현이 갈라질 때 곧바로 보안 사고가 됩니다. 확장은 wasm, 서버는 네이티브로 같은 crate를 씁니다.
ADR-0003
서버 저장소 — SQLite
파일 하나로 자체 호스팅이 쉽고, DKG처럼 여러 단계를 거치는 작업을 트랜잭션으로 묶어 반쪽 상태를 막습니다. 셰어는 앱에서 암호화한 뒤 저장합니다.
ADR-0004
MPC 라이브러리 재선정 — 0xCarbon/DKLs23
키 리프레시를 지원하는 유일한 permissive 후보입니다. 리프레시가 없으면 복구가 주소 변경을 동반한 이전이 됩니다. 감사 이력이 없어 자체 감사 비용을 부담하고, 버전 고정과 추상화 계층으로 교체 가능성을 유지합니다. 구현 후 실측에서 모든 기준을 통과했습니다.
발견 · Phase 1
리프레시는 기존 파티 전원을 요구한다
셰어를 잃은 자리를 새 기기로 채우는 것은 리프레시가 아니라 리셰어인데, 업스트림에 해당 프로토콜이 없습니다. 현재 계획은 사용자 기기에서 키를 복원해 즉시 다시 나누는 것이며, 이 순간 개인키가 잠깐 한 곳에 존재합니다. 서버는 이 과정을 보지 않고, 사용자에게 고지합니다.
발견 · Phase 1
업스트림이 현재 stable 의존성에서 빌드되지 않는다
채택한 라이브러리는 RustCrypto pre-release에 맞춰 발행되었는데 그 뒤 stable이 나왔습니다. 해당 버전을 고정해 해결했고, 업스트림에 보고할 예정입니다. 감사와 유지보수 비용을 우리가 진다는 판단이 실제로 맞았다는 첫 사례입니다.

저장소

구조

crates/mpc-core     프로토콜 코어 — 확장과 서버가 공유하는 단일 진실 공급원
crates/mpc-wasm     wasm 바인딩 — 타입 변환만, 프로토콜 로직 없음
crates/mpc-server   셰어 C 보관 + DKG · 복구 참여 (axum · SQLite · Swagger UI)
packages/extension  크롬 확장 (MV3 · React · WXT)
packages/sdk        웹페이지용 provider SDK (EIP-1193 / EIP-6963)
docs/               설계 문서와 ADR
AGENTS.md           개발 대전제 (CLAUDE.md는 심볼릭 링크)

make check가 커밋 게이트입니다 — 포매팅, clippy(경고를 에러로), TypeScript strict, 테스트를 한 번에 돌립니다. copyleft 의존성은 cargo-deny가 기계적으로 막습니다.
