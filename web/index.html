mpc-ext/2-of-3

A key split into three pieces, one in each of three different places: the extension, a recovery file you keep, and the server. Day to day the extension and the server sign together, so compromising either one alone cannot produce a signature.

unaudited · not for real assets DKLs23 · secp256k1 Rust + wasm · MV3 Apache-2.0

How it works

Three shares, two of them sign

The complete private key exists nowhere. Two of the three shares have to come together to produce a signature, and even then the key is never assembled. Because the three live in different places, breaching any one of them still cannot sign. Pick a situation below to see which shares take part.

2 / 3 can sign — extension and server together

The extension and the server each bring one share. The server is a second factor, not a vault — if the extension is compromised and the server refuses, no signature is produced.

Stated plainly

What we gave up

Splitting the shares across three places costs us two things. We would rather write them down than hide them.

  • The server takes part in every signature. It learns what you sign, and when it is down you have to fetch your recovery file and sign with A+B instead. Censorship becomes possible.
  • Every signature needs a network round trip. The computation takes 16 ms, but perceived latency is dominated by the round trip.

And there are two assumptions you can break yourself.

  • Keeping the recovery file on the same machine as the extension puts two shares in one place. Take over that machine and signing becomes possible, which defeats the whole design.
  • Losing the recovery file and the device together is unrecoverable, because only the server share would remain.

Measured

Is it fast enough in a browser?

We set budgets before choosing a library, then checked them against the real implementation. Mean of five runs; the wasm figures drive all three parties on one V8 thread.

Operation Native wasm (V8) Budget Result
Signing (2 parties) 4.4 ms 16 ms 1 s pass
DKG (3 parties) 833 ms 4,920 ms 10 s pass
Key refresh (3 parties) 834 ms 4,868 ms 30 s pass

Everyday signing takes 16 ms. The path you use daily has no perceptible delay. Key creation and refresh take close to five seconds, but both are rare. The wasm bundle is 459 KB after optimisation, 174 KB gzipped.

Decision record

Choices that are hard to undo

Stack swaps, protocol changes and storage format changes are recorded as ADRs. Withdrawn decisions are kept too, along with why they were withdrawn.

ADR-0001
MPC library — silence-laboratories/dkls23
Withdrawn. We read it as Apache-2.0; it is in fact non-commercial, revocable and non-redistributable, which an open-source project cannot use.
ADR-0002
Stack — one Rust core shared by extension and server
Implementing the protocol twice means the two eventually diverge, and for crypto that divergence is a security incident. The extension consumes the crate as wasm, the server natively.
ADR-0003
Server storage — SQLite
A single file makes self-hosting easy, and multi-step operations such as DKG commit in one transaction so no half-finished state survives. Shares are encrypted by the application before storage.
ADR-0004
MPC library, take two — 0xCarbon/DKLs23
The only permissively licensed candidate that supports key refresh. Without refresh a recovery becomes a migration with a new address. It has no audit history, so we budget for one ourselves, and we keep it replaceable with a version pin and a boundary layer. Once implemented, it passed every budget we had set.
Finding · Phase 1
Refresh requires every existing party
Filling the slot of a lost share on a new device is a reshare, not a refresh, and upstream has no such protocol. Our approach reconstructs the key on the user's device and immediately re-splits it, so the private key briefly exists in one place. The server never sees this, and we tell the user it happens.
Finding · Phase 1
Upstream does not build against current stable dependencies
The library was published against RustCrypto pre-releases, and stable has since landed. We fixed it by pinning those versions, and we will report it upstream. It is the first concrete instance of the maintenance cost we assumed we would be carrying.

Repository

Layout

crates/mpc-core     protocol core — the single source of truth, shared by both sides
crates/mpc-wasm     wasm bindings — type conversion only, no protocol logic
crates/mpc-server   holds share C, joins DKG and signing (axum, SQLite, Swagger UI)
packages/extension  the Chrome extension (MV3, React, WXT)
packages/sdk        provider SDK for web pages (EIP-1193 / EIP-6963)
docs/               design documents and ADRs
AGENTS.md           ground rules for contributors (CLAUDE.md symlinks here)

make check is the commit gate: formatting, clippy with warnings as errors, strict TypeScript and the test suite in one command. cargo-deny mechanically blocks copyleft dependencies.
